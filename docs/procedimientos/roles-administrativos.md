## El script `admin:assign-role`

Desde `backend/`. **Por defecto solo simula y solo lee.**

```
npm run admin:assign-role -- --listar
npm run admin:assign-role -- --email=<correo> --rol=<ROL>
npm run admin:assign-role -- --email=<correo> --rol=<ROL> --apply --confirmar=<correo> --destino=<host>:<puerto>/<base> --servidor=<server_uuid> --operador=<identificador> --motivo=<texto>
```

### Auditoría desde la terminal (E3.2, pendiente de revisión)

`admin:assign-role --apply` y `admin:create` registran cada cambio efectivo en `admin_auditoria` con `origen='terminal'`, `actor_id` nulo, el **operador declarado** (`--operador`), el **motivo** (`--motivo`), la cuenta afectada, el rol anterior y el nuevo (o el alta) y la fecha del servidor. El cambio y su registro van en la **misma transacción**: si el registro falla, se revierten también el rol y `session_version` (o no se crea la cuenta). Si falta la tabla, o está incompleta, la simulación y la aplicación se detienen antes de bloquear o escribir e indican aplicar `20261014-admin-auditoria`; `--listar` lo avisa.

- **`--operador` no es autenticación.** Identifica a quien *declara* ejecutar el script; cualquiera con acceso a la terminal y a las credenciales de la base puede escribir otro valor. Es una constancia, no un control: la protección real sigue siendo el acceso restringido a la terminal y a la base. Use un identificador corto (iniciales o código de puesto), no correos: el operador admite solo letras, números, espacios, `.`, `-` y `_` (2–100 caracteres).
- **`--motivo`**: 5–200 caracteres en una línea, sin `@`. No incluya contraseñas ni datos personales.
- Los intentos rechazados y las operaciones sin cambios **no** se registran (el script imprime el motivo del rechazo).

### Confirmación del destino (qué garantiza y qué no)

1. **Una sola configuración.** Al arrancar, el script carga `database.cjs`, que lee el `.env` del directorio actual (dotenv) y, al importar Prisma, también `backend/.env` para las variables que falten; las variables del proceso prevalecen sobre ambos archivos. Esa configuración se resuelve **una vez**, antes de validar nada, y la conexión se abre forzando ese mismo host, puerto y base. Lo que se confirma es lo que se usa.
2. **`--destino=<host>:<puerto>/<base>`** debe coincidir exactamente con la configuración resuelta (incluido el puerto: dos servidores en el mismo host con la misma base se distinguen). Si no coincide, el script **se detiene sin conectarse** y muestra el destino configurado. Esto comprueba la *configuración*, no el servidor.
3. **Base real.** Tras conectar, `DATABASE()` debe ser exactamente la base configurada; si no, se detiene sin leer ni escribir cuentas (también en `--listar` y en la simulación).
4. **`--servidor=<server_uuid>`** identifica al servidor MySQL realmente conectado (`@@server_uuid`). `--listar` y la simulación lo muestran junto con la línea de confirmación completa. Para escribir, el valor debe coincidir; si no coincide o no se puede obtener, **no se escribe nada**.
5. El *hostname* y el *puerto* que informa MySQL (`@@hostname`, `@@port`) se muestran solo como referencia: con Docker, proxies o nombres DNS pueden diferir legítimamente del host y puerto configurados, por lo que **no** se usan como prueba de identidad.

Límites: `server_uuid` demuestra que la escritura ocurre en el **mismo** servidor que se listó o simuló, no que ese servidor sea el correcto. Compare el valor con la identidad conocida del destino (anotada por el responsable, p. ej. con `SELECT @@server_uuid` desde la consola del proveedor). Una copia del directorio de datos de MySQL (clonación de un servidor) puede conservar el mismo `server_uuid`; por eso también se exigen host, puerto y base.

Salvaguardas:

- Sin `--apply` no abre transacciones ni escribe. Con `--apply` exige repetir el correo exacto (`--confirmar`), el destino configurado (`--destino`) y la identidad del servidor conectado (`--servidor`), según el apartado anterior. Las opciones repetidas o incompatibles se rechazan.
- Solo asigna roles a cuentas **existentes y activas**; no crea cuentas, no cambia contraseñas ni correos y no activa ni desactiva cuentas. **No puede retirar un rol** (volver a «sin rol») ni cambiar el de una cuenta desactivada: solo cambia entre los tres roles (ver M-2).
- Nunca deja al sistema **sin un `GERENTE_GENERAL` activo**: el primer rol asignado en una base sin gerente tiene que ser `GERENTE_GENERAL`, y no se puede degradar al último gerente.
- Dar `GERENTE_GENERAL` a una segunda cuenta exige `--permitir-otro-gerente` (para que el acceso completo no se conceda por accidente).
- **Toda** asignación o cambio de rol, incluida la primera, sube `session_version` de esa cuenta: cierra sus sesiones abiertas y obliga a iniciar sesión de nuevo (decisión aprobada). Las demás cuentas no se tocan.
- Escribe dentro de una transacción con las filas bloqueadas (`FOR UPDATE`) y con un bloqueo de MySQL contra ejecuciones simultáneas; revalida con esas filas y comprueba el resultado final antes de confirmar. Si algo cambió o falla, revierte.
- No lee la columna de contraseñas ni muestra usuario, contraseña o cadena de conexión. Los listados enmascaran los correos (`ab***@dominio`). Si falta la columna `rol`, se detiene e indica aplicar la migración.
- Cada ejecución imprime el destino, la cuenta, el rol anterior y el nuevo, y con `--apply` exige `--operador` y `--motivo` (ver «Auditoría desde la terminal»).

## El script `admin:create`

Crea una cuenta activa **sin rol** (`rol = NULL`), también cuando todavía no hay ningún gerente: nunca concede `GERENTE_GENERAL` ni otro rol. Desde `backend/`, con la contraseña inicial en una variable temporal (nunca en argumentos):

```
ADMIN_INITIAL_PASSWORD=<temporal> npm run admin:create -- --destino=<host>:<puerto>/<base> --servidor=<server_uuid> --operador=<identificador> --motivo=<texto>
```

Pide nombre y correo. Confirma el destino con las **mismas comprobaciones que `admin:assign-role`** (apartado «Confirmación del destino», misma implementación): `--destino` debe coincidir con la configuración resuelta y, si no, se detiene sin conectarse; `--servidor` es obligatorio y debe ser un `server_uuid` completo (si falta o está mal formado, se detiene sin conectarse); tras conectar, `DATABASE()` debe ser esa base y `@@server_uuid` debe coincidir con `--servidor`. Si la base es otra, el servidor es otro o no informa su `server_uuid`, **no se escribe nada** (ni siquiera se calcula el hash). El `server_uuid` y la línea de confirmación los muestra `npm run admin:assign-role -- --listar` (solo lectura). Todas las comprobaciones (destino, servidor, migraciones, correo duplicado) ocurren antes de abrir la transacción. Rechaza correos duplicados (también dos altas simultáneas: gana una). El alta y su registro de auditoría se confirman juntos en una única transacción: si el registro falla, no se crea la cuenta. La cuenta se crea siempre con `rol = NULL`. No imprime la contraseña, su hash ni las credenciales de conexión; el correo se muestra enmascarado.

## Cuentas creadas desde el registro público

`/admin/register` (`POST /api/admin/signup`) permite que cualquier visitante cree una cuenta **activa y sin rol**; el alta queda en `admin_auditoria` como `cuenta_creada` con `origen = panel`, `actor_id` NULL y un `motivo` que indica el registro público. La cuenta puede iniciar sesión de inmediato y el panel la lleva a «Mi espacio»: una cuenta básica que consulta sus datos y cambia su contraseña desde Ajustes, sin ninguna sección administrativa. Sin rol no obtiene permisos administrativos: el backend mantiene JWT, AccessGuard y RBAC y le deniega toda ruta con permiso (403). El formulario no admite elegir rol ni ningún otro campo privilegiado (el backend responde 400). Para autorizar a una persona, la gerencia comprueba su identidad por un canal propio y el gerente le asigna el rol desde «Roles y usuarios» (con confirmación y auditoría) o con `admin:assign-role` (procedimiento auditado de este documento). El registro no verifica el correo: alguien podría registrarse con un correo ajeno, pero esa cuenta no obtiene funciones administrativas sin la asignación de rol y su titular real puede recuperarla con «Olvidé mi contraseña».

## Plan seguro para asignar al primer gerente

Requiere autorización expresa del responsable; no lo ejecuta ningún proceso automático.

1. Confirmar el entorno y su destino (`DB_HOST`, `DB_PORT`, `DB_NAME`) y obtener, por una vía independiente, el `server_uuid` del servidor de destino.
2. Respaldo: `npm run db:backup -- --dir=<volumen persistente>` (ver `backup-restauracion.md`) y comprobar que existe.
3. `npm run db:check` (solo lectura). Antes de migrar se espera que informe `admin_users.rol: falta`.
4. `npm run db:migrate`; después `npm run db:check` debe terminar en «Esquema compatible».
5. `npm run admin:assign-role -- --listar`. Comprobar que «Destino configurado», la base y el `server_uuid` mostrados son los esperados. **El responsable identifica cuál cuenta es la del gerente**; no se deduce por orden ni por antigüedad.
6. Simular: `npm run admin:assign-role -- --email=<correo del gerente> --rol=GERENTE_GENERAL` y revisar cuenta, rol, conteo de gerentes y la línea de confirmación.
7. Aplicar con `--apply --confirmar=<correo> --destino=<host>:<puerto>/<base> --servidor=<server_uuid> --operador=<identificador> --motivo=<texto>`, usando valores comprobados en los pasos 1 y 5.
8. Comprobar con `--listar` (debe mostrar 1 gerente activo) y guardar la salida.
9. Las demás cuentas **quedan sin rol** (`NULL`). Nada las eleva. Con el control de acceso activo, una cuenta sin rol solo puede consultar su sesión y cambiar su contraseña (en el panel, «Mi espacio» y Ajustes). Las cuentas que ya no correspondan (por ejemplo, del antiguo puesto administrativo) se **desactivan, no se borran**, desde «Roles y usuarios» o por el procedimiento que se autorice.
10. Asignar los demás roles uno a uno con el mismo script (simulación primero) o, con el gerente ya activo, desde «Roles y usuarios».

## Recuperación ante fallos

| Situación | Qué hacer |
| --- | --- |
| El script falla o se interrumpe | La transacción se revierte; vuelva a ejecutar `--listar` para ver el estado real y repita la simulación. El bloqueo de MySQL se libera al cerrar la conexión. |
| Se asignó el rol a la cuenta equivocada | Asigne `GERENTE_GENERAL` a la cuenta correcta con `--permitir-otro-gerente`, y después cambie la equivocada a otro de los tres roles (todo cambio de rol cierra las sesiones de esa cuenta). **El script no puede dejarla «sin rol»**, pero el gerente sí puede retirarle el rol desde «Roles y usuarios» (queda como cuenta básica y se cierran sus sesiones). Si no debe tener ningún acceso, desactívela: la desactivación le retira el rol (M-2) y, si se reactiva, vuelve sin rol. No se puede quitar el rol del último gerente activo, a propósito. |
| El gerente olvida su contraseña | Flujo normal «Olvidé mi contraseña» (`/admin/forgot-password`); no requiere el script. |
| El gerente pierde también el acceso a su correo, o la cuenta quedó desactivada | Seguir «Recuperación del acceso administrativo» (abajo): crear otra cuenta sin rol con `admin:create` y darle `GERENTE_GENERAL` con `admin:assign-role`. La cuenta desactivada se tratará después. |
| La migración causó un problema | La columna es nula y aditiva; no hace falta deshacerla. Si fuera imprescindible volver al estado anterior, restaure el respaldo previo (`backup-restauracion.md`) y vuelva a ejecutar `db:migrate`. No se proporciona un `DROP COLUMN`. |
| El backend se desplegó antes que la migración | El inicio de sesión fallará: aplique `db:migrate` de inmediato (es aditiva y rápida). Evítelo aplicando la migración antes de desplegar. |

### Recuperación del acceso administrativo

Cuando ninguna cuenta con acceso puede entrar (por ejemplo, el único gerente quedó desactivado o perdió su correo). Requiere autorización expresa del responsable, acceso a la terminal del backend y a la base, y un respaldo previo. Desde `backend/`:

1. **Identificar el servidor en solo lectura:** `npm run admin:assign-role -- --listar`. Muestra «Destino configurado», la línea «Servidor conectado» (base real y `server_uuid`), las cuentas con el correo enmascarado, el número de gerentes activos y la línea de confirmación `--destino=… --servidor=…`.
2. **Confirmar host, puerto, base y `server_uuid`** con la identidad conocida del destino, obtenida por otra vía (consola del proveedor o anotación del responsable). Si algo no coincide, detenerse.
3. **Crear una cuenta sin rol:** `ADMIN_INITIAL_PASSWORD=<temporal> npm run admin:create -- --destino=<host>:<puerto>/<base> --servidor=<server_uuid> --operador=<identificador> --motivo=<texto>`, con los valores comprobados en el paso 2. Retirar la variable al terminar.
4. **Asignar `GERENTE_GENERAL`:** simular con `npm run admin:assign-role -- --email=<correo> --rol=GERENTE_GENERAL` y aplicar con `--apply --confirmar=<correo> --destino=<host>:<puerto>/<base> --servidor=<server_uuid> --operador=<identificador> --motivo=<texto>`. Si no queda ningún gerente activo no hace falta `--permitir-otro-gerente`; si aún queda alguno, sí.
5. Comprobar con `--listar` (al menos un gerente activo) y guardar la salida. El alta y la asignación quedan en `admin_auditoria` con el operador y el motivo declarados.

**Si el esquema está atrasado.** `--listar` funciona sin la tabla `admin_auditoria`: termina normalmente y avisa de que falta `20261014-admin-auditoria`. Sin la columna `admin_users.rol` (migración `20261014-admin-rol`) se detiene con error **después** de imprimir la línea «Servidor conectado» con la base y el `server_uuid`, que sirven igualmente para el paso 2 (comprobado en M-3). Si el script no llega a conectar, use una consulta de solo lectura en la consola de MySQL del destino: `SELECT DATABASE(), @@server_uuid, @@hostname, @@port;` (sin modificar nada). En ambos casos `admin:create` y `admin:assign-role` se niegan a escribir hasta reparar el esquema, en este orden: respaldo (`npm run db:backup -- --dir=<volumen persistente>`), `npm run db:check` (solo lectura; indica qué falta), `npm run db:migrate` (aplica `20261014-admin-rol` y después `20261014-admin-auditoria`), `npm run db:check` («Esquema compatible») y, entonces, los pasos 1–5. Tenga en cuenta que sin `admin_users.rol` el inicio de sesión del backend actual también falla (ver la tabla anterior).

## Autorización por roles: preparada en E3.3, activa en el código candidato de E3.6

- **Clasificación de rutas.** Cada ruta HTTP declara su acceso con un decorador de `src/permissions/access.decorators.ts`: `@PublicRoute()`, `@AuthenticatedRoute()` (autoservicio: `/admin/me` y cambio de la propia contraseña, también sin rol), `@RequirePermission(p)`, `@RequireFollowUp(op)` (el permiso depende de `:recurso`) o `@RequireByField(campo, base, {valor: permiso})` (pasar a «archivado» o «anulada» exige además archivar o anular). Los decoradores solo añaden metadatos. Una prueba exige que coincidan con el inventario escrito a mano (`route-inventory.ts`) y que ninguna ruta quede sin clasificar.
- **`AccessGuard`** (`src/permissions/access.guard.ts`): una ruta pública pasa sin sesión. Las demás reutilizan `JwtAuthGuard` sin cambios y responden 401 si falta la sesión o no es válida. En las rutas con permiso, la guard relee de la base `activo`, `session_version` y `rol`: si no coinciden con el token, 401; sin rol (o con un valor desconocido), 403 con «Esta función requiere permisos adicionales. Tu cuenta es básica…» (`NO_ROLE_MESSAGE`); sin el permiso, 403. Deniega por defecto: una ruta sin decorador, con una declaración inválida o con un recurso de seguimiento desconocido responde 403, también al gerente. El rol nunca se toma del JWT, de las cabeceras ni del cuerpo.
- **Registro (E3.6, local, sin desplegar).** AppModule la registra como `APP_GUARD` después de `PublicRateLimitGuard` (un intento denegado en una ruta limitada consume cuota), con `JwtAuthGuard` y `AccountAccessService` como proveedores. Ningún otro módulo la registra; una prueba lo exige. Antes de E3.6 no la registraba ningún módulo y las rutas administrativas solo exigían `JwtAuthGuard`.
- **Contrato de sesión (E3.4.1).** `POST /admin/login` y `GET /admin/me` conservan sus campos y añaden, en `user`, `rol` (uno de los tres roles o `null`) y `permisos` (calculados con la matriz de `policy.ts`; `[]` sin rol o con un valor desconocido), y `acceso: { modo }`. El rol sale de la base: en `/admin/me`, de la misma lectura con la que `JwtStrategy` comprueba la cuenta activa y `session_version` (sin consulta adicional); en el login, de la fila recién leída. El JWT no cambia (`id`, `email`, `version`): ni rol ni permisos viajan en el token, y lo que envíe el cliente (JWT, cabeceras, cuerpo) no cuenta. `/admin/me` responde 200 también sin rol y 401 si la sesión no es válida. Esta información solo sirve para que el panel adapte la interfaz: **ocultar una opción no protege nada** mientras la guard no esté activa.
- **Cómo lo interpreta el panel (E3.4.2).** El contexto de autenticación de React lo guarda solo en memoria (`access`; nunca en localStorage). Con el contrato completo el login no necesita otra consulta; un backend antiguo (sin esos campos) se valida con `/admin/me` y queda en modo heredado, sin rol ni permisos; una respuesta incompleta o incoherente no abre el panel. Un 403 no cierra la sesión; un 401 sí. React no duplica la matriz de permisos.
- **Menú por permisos (E3.4.3, fase 1).** `frontend/src/panel/context/panelAccess.ts` declara cada sección con el permiso de lectura del GET que carga al abrirse (el mismo de `route-inventory.ts`; una prueba los contrasta) y decide con la lista `permisos` de la sesión, sin mirar el nombre del rol:

  | Situación | Menú | Inicio |
  | --- | --- | --- |
  | Backend antiguo (`contract: 'antiguo'`) | Navegación heredada completa, sin permisos inventados | Resumen |
  | Modo `heredado`, rol `null` | Navegación heredada completa (temporal) | Resumen |
  | Rol válido, modo `heredado` o `por_roles` | Solo las secciones cuyo permiso de lectura figura en `permisos` | Resumen si tiene `estadisticas:leer`; si no, la bandeja |
  | Modo `por_roles`, rol `null` (cuenta básica) | Solo «Mi espacio», sin secciones administrativas; Ajustes de su cuenta y cerrar sesión | «Mi espacio» (`PanelBasicHome`), sin bloqueo |
  | Sesión sin validar o contrato inválido | Nada (pantalla de carga o de error y reintento de siempre) | — |

  Con la matriz actual: gerente, todo el menú; coordinadora, todo salvo la Biblioteca de contenido (`items:leer`); secretaria, Educación (solo Capacitaciones y Cursos, porque Asesoramiento es un servicio), Mensajes, Consultas del chatbot e Información de empresa, con inicio en la bandeja (no tiene `estadisticas:leer`, así que no consulta `GET /admin/stats`). Una sección sin permiso, también por enlace directo (`/admin/dashboard?section=cotizaciones`), muestra «No tienes acceso a esta sección» con un enlace a su inicio, sin redirigir y **sin montar el componente**, de modo que no hace solicitudes. Una sección desconocida abre el inicio de la cuenta, como antes. «Roles y usuarios» (antes «Cuentas y acceso», `PanelAccounts`) solo se muestra y se monta con `por_roles` y `cuentas:leer` (hoy, solo el gerente). Un 403 al cambiar la contraseña ya no se presenta como «Tu sesión venció».
- **Operaciones por permisos (E3.4.3, fase 2, implementada localmente, sin publicar).** `RESOURCE_WRITE` y `PANEL_ACTIONS` (en `panelAccess.ts`) declaran el permiso de cada escritura del panel, el mismo que exige su ruta en `route-inventory.ts` (`test:panel-access` los contrasta, incluidos los PUT que exigen además archivar o anular). Las secciones consultan `usePanelAccess().can(permiso)`, que en navegación heredada (backend antiguo o cuenta sin rol en modo `heredado`) lo ofrece todo, como antes; con rol, solo lo que figura en `permisos`; y sin rol en `por_roles`, nada. Sin el permiso de una operación:
  - su botón o enlace no se muestra (crear, editar, duplicar, eliminar o archivar, «Recuperar contenido original», publicar u ocultar convenios, enviar o anular cotizaciones, registro manual, cambios de estado, «Eliminar consulta…», envíos de correo del seguimiento); los enlaces del Resumen y de la bandeja hacia secciones que la cuenta no puede abrir, o accesos de creación sin `…:crear`, tampoco («Preparar cotización» exige abrir Cotizaciones y `cotizaciones:crear`);
  - los registros se abren en **modo consulta**: campos deshabilitados, sin guardar, con el aviso «Modo consulta…» cuando la sección entera es de lectura (Información de empresa sin `configuracion:editar`, Cursos y Capacitaciones de la secretaria, convenios, cotizaciones y seguimiento de una cuenta que solo lee);
  - `?crear=1` (catálogo y Mensajes) y `?contacto=` (Cotizaciones) no abren el alta: se muestra la sección con un aviso;
  - el estado «Archivado» no se ofrece sin `…:archivar` (salvo para mostrar un registro que ya lo está), y guardar un registro archivado sin ese permiso se detiene con un aviso, porque el backend exige archivar cuando el cuerpo trae `estado: archivado`;
  - cada función que envía una escritura vuelve a comprobar el permiso antes del POST, PUT o DELETE, de modo que tampoco sale con Enter ni con una dirección.

  Con la matriz actual: la secretaria ve Cursos, Capacitaciones e Información de empresa en modo consulta, registra consultas (también con `?crear=1`), cambia su estado y responde, pero no las elimina ni prepara cotizaciones; la coordinadora gestiona el contenido salvo borrar servicios (`servicios:eliminar`), no recupera contenido original, no elimina consultas y ve Información de empresa en modo consulta; el gerente dispone de todos los permisos. El permiso `cursos:eliminar` permanece en la matriz y en el decorador, pero no habilita borrado físico: el servicio responde 409 para un curso o capacitación existente sin modificarlo (404 si no existe). Ninguna cuenta dispone de ese botón, tampoco en modo heredado. El archivado se hace desde Editar por PUT y exige `cursos:editar` y `cursos:archivar` en el panel; los archivados se consultan en la administración y pueden republicarse. Servicios conserva eliminación definitiva y FAQ, archivado mediante DELETE. Con la guard inactiva, la restricción por rol sigue siendo de interfaz; la protección de conservación de cursos sí se aplica en el backend a cualquier sesión válida.
- **Modo de acceso.** `ACCESS_MODE` (`src/permissions/session-access.ts`) vale `por_roles` desde E3.6, porque AccessGuard está registrada (antes, `heredado`). Activar o revertir es cambiar ambos a la vez, sin variables de entorno. Una prueba exige que el valor coincida con el registro real en `app.module.ts` en ambos sentidos, para que nunca se anuncie una protección que no existe.
- **Ajuste de matriz (E3.4.1).** `mensajes:crear` (registrar una consulta manual, `POST /admin/messages`) se concede a los tres roles por ser parte de la atención al público. `mensajes:eliminar` sigue siendo exclusivo del gerente; no cambia ningún otro permiso.
- **Al activarla (E3.6; comprobado con HTTP real en cuentas ficticias):** la secretaria y la coordinadora perderán `POST /admin/register`, `GET /admin/users` y `PUT /admin/users/:id` (reservados al gerente). Las cuentas sin rol solo conservarán el autoservicio, así que antes hay que asignar los roles (`admin:assign-role`). Lecturas de la cuenta por clave primaria (recuento según el código, no medición de rendimiento): una ruta con permiso pasa de 1 lectura (`JwtStrategy` desde el `JwtAuthGuard` local) a 3 (`JwtStrategy` desde AccessGuard, `AccountAccessService` y de nuevo `JwtStrategy` desde la guard local), es decir, 2 adicionales; una ruta de autoservicio pasa de 1 a 2 (1 adicional); una pública sigue sin lecturas. Detalle en [activacion-accessguard.md](activacion-accessguard.md#lecturas-de-la-cuenta-por-solicitud).

## Decisiones aprobadas y pendientes

Aprobadas: toda asignación de rol sube `session_version`; se mantienen las confirmaciones estrictas (`--apply`, correo, destino con puerto, identidad del servidor, segundo gerente); las cuentas no identificadas permanecen sin rol; los campos de trazabilidad de asignaciones (quién y cuándo) se incorporarán con la auditoría; **el primer gerente lo identifica expresamente el responsable** (no se deduce), y la cuenta de desarrollo se mantiene separada de las de producción.

Pendientes: cuándo y cómo se ejecuta la migración en cada entorno (local, Railway) y quién la autoriza; qué hacer con las cuentas actuales que no correspondan (propuesta: desactivarlas, no borrarlas).
